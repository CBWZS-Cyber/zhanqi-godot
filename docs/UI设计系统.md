## 一、为什么要有它

2026-10-04 审计 UI 层，量出来的事实：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| `Color(...)` 硬编码字面量 | **373 处** | **147 处**（剩下的都是透明遮罩/一次性装饰色） |
| 不同字面量种类 | 188 种 | 111 种 |
| 同一个金写了几遍 | **19 遍 / 9 个文件** | 1 处令牌 |
| 同一个面板色写了几遍 | 5 遍（**alpha 还各不相同** 0.94 / 0.90 / 0.97） | 1 处令牌 |
| "灰蓝小字"有几种 | **7 种，彼此差不到 3%** | 3 级（INK_200/250/300） |

三条实证病根：

1. **同名不同值** —— `COL_PANEL` 在 4 个文件各写一遍，alpha 一个是 0.94、一个是 0.9。肉眼看不出来，但改一处不影响另一处，于是永远改不干净。
2. **语义冲突** —— `COL_RED` 同时当"我方阵营色"和"血量条色"，想统一血量条就会连带改掉队伍色。
3. **两套体系打架** —— 界面框架是冷调深蓝 + 金，棋盘是暖木 + 羊皮纸，中间靠一行 `COL_BORDER` 硬缝，观感"拼"。

## 二、三条设计原则

### 1. 金是唯一的强调色
全工程只有 `GOLD_500` 承担强调。**一屏只允许一个金底按钮**（主 CTA）。次级操作一律墨底金边。

### 2. 弹窗背景不透明（硬规矩）
`SURFACE_MODAL = INK_900`，alpha 恒为 1.0。半透明的只有 `SURFACE_PANEL`——那是**棋盘上的对局侧栏**（需要看得到棋盘），不是弹窗。两者在代码与测试里明确区分。

### 3. 编号与亮度同序
墨阶 950 → 050、金阶 700 → 100，数字越小越亮。**顺序错乱会让层级关系被读反**——这条由测试 C 段强制（它已经抓出过一次真实倒挂）。

#### ⚠️ 资源条必须「四色四义」（2026-10-04 立，用户实报要求）

| 资源 | 令牌 | 颜色 |
|---|---|---|
| 生命 | `HP` | 绿 |
| 护盾 | `SHIELD` | 蓝 |
| 能量 | `ENERGY` | **琥珀** |
| 理智 | `SANITY` | 紫 |

这条规矩是被真实 bug 逼出来的 —— 改前**同一个「能量」有三种颜色**：

| 位置 | 改前 | 改后 |
|---|---|---|
| 棋子头顶迷你条 | 琥珀 `0.85,0.65,0.25` | `ENERGY`（值不变） |
| 对局侧栏 | **`COL_BLUE` = 敌方阵营蓝** | `ENERGY` |
| 教程面板 | 蓝 `0.35,0.62,0.90` | `ENERGY` |

而且 `SHIELD`（蓝）与旧 `ENERGY`（蓝）几乎同色 → **盾和能量根本分不出**。

规矩三条：
1. **不许拿阵营色当资源色**（侧栏能量条曾用 `COL_BLUE`）。
2. **不许把生命与护盾画进同一根条、只靠颜色分** —— 细条上（3~22px）看不出谁是谁。
   要么分两条，要么加**深色分隔线**（`BAR_EDGE`）。
3. 四色**两两通道差 ≥ 0.25**，由测试 H 段强制。

## 五、组件库用法

**界面代码里不许再写 `Color(...)`。** 要颜色从令牌取，要样式走组件库。

```gdscript
# 按钮（四类：primary 全屏唯一 / secondary 默认 / ghost 低频 / danger 危险）
UiTheme.style_button(btn, UiTheme.KIND_PRIMARY)

# 输入框（自动带聚焦金环 + min_x/min_y 供 _fit 缩放）
UiTheme.style_input(edit, 420.0, 48.0)

# 卡片 / 弹窗（弹窗强制不透明 + 金边 + 重投影）
UiTheme.style_card(panel)
UiTheme.style_modal(dialog)

# 场景根挂主题（幂等，重复调用无害）
func _ready() -> void:
    UiTheme.attach(self)
```

**注意样式优先级：控件 override > Theme。** 所以挂 Theme 不会破坏任何既有观感，只会补齐缺失的部分（Tooltip / PopupMenu / 滚动条 / 焦点环）。

### 在 Godot 里运行时取令牌
```gdscript
const COL_GOLD := UiDesign.GOLD_500          # 常量引用（推荐）
var c := UiDesign.contrast(UiDesign.INK_100, UiDesign.SURFACE_CARD)
var t := UiDesign.text_on(some_bg)           # 自动挑对比度更高的文字色
```

> ⚠️ **不要** `preload("...ui_design.gd")` 之后用 `_D.contrast(...)` 调静态函数 ——
> preload 拿到的是 GDScript 资源，**只有常量能从它上面取**，静态函数取不到
> （会报 `Nonexistent function 'contrast' in base 'GDScript'`）。直接用全局类名。

### 字体三档

**小字要清晰，大字要有性格。** 一副字体做不好这两件事，所以分三档，档位之间是**硬字号阈值**。

| 档位 | 字体 | 用在哪 | 体积 |
|---|---|---|---|
| 主视觉 | 马善政毛笔楷书 | **≥60px**：主菜单「战棋」、结算 / 胜利标题 | 5.6 MB |
| 小标题 | 思源宋体 Bold | **≥22px**：面板标题 / 章节名 / 关卡名 / 英雄名 | 11.5 MB |
| 正文 | 思源黑体（**可变字重**） | **<22px**：正文 / 按钮 / 数值 / 标签 | 17.0 MB |

```gdscript
# 标题：套到 Label 上（按字号自动选档）
UiTheme.style_title(title_label, 44)     # 44 → 宋体；80 → 毛笔（带字距）；20 → 正文

# 取字体本体
var f_hero:  Font = UiTheme.hero_font()              # 毛笔（可传 tracking）
var f_title: Font = UiTheme.serif_font()             # 宋体
var f_body:  Font = UiTheme.body_font()              # 黑体 Regular
var f_btn:   Font = UiTheme.body_font(UiTheme.W_MEDIUM)   # 黑体 Medium（按钮）
```

**五条规矩：**

1. **阈值不能"顺手调低"**：毛笔字在 22px 会糊成一团，宋体在 14px 不如黑体清楚。
   所以 `title_font()` 的分档是硬编码的，不是可调参数。
2. **字距随字号缩放**（`FontVariation.spacing_glyph`）：80px→7 ／ 60px→5。
   毛笔体 + 字距是「设计感」的主要来源，比换字体本身更明显。
3. **字体缺失必须优雅降级**为正文字体，**绝不返回 null**（否则整屏文字消失）。
   降级是**静默**的 —— 所以测试 I 段会断言三档字体**真的加载到了**。
4. **正文要用可变字重**：按钮 Medium(500)、主 CTA SemiBold(600)、正文 Regular(400)。
   系统字体只给得到一个 400，界面会显得「平」；这也是打包 17 MB 黑体的**主要理由**。
5. **不许让引擎隐式兜底**字体。`SystemFont` 只作为打包字体缺失时的最后退路。

> 字体全部 OFL 授权，**分发时必须随包附 `assets/fonts/LICENSE-*.txt`**。

### RichText 内联色：`MD_*` 调色板

bbcode 只能吃 `#RRGGBB` 字符串，没法引用 `Color` 令牌，所以 `UiDesign` 里单独有一组
`MD_*` 常量，**值由同义令牌派生**（J 段会逐个校验一致）：

| 常量 | 值 | 同源令牌 | 用途 |
|---|---|---|---|
| `MD_OK` | `#5EBF73` | `OK` | 地形 / 技能名 / 加成 |
| `MD_GOLD` | `#FFE08C` | `GOLD_400` | 标题 / 武器名 |
| `MD_HL` | `#FFD95A` | `GOLD_HL` | 正文内联高亮 |
| `MD_DIM` | `#ADB8CC` | `INK_300` | 次要说明 |
| `MD_MUTED` | `#949EB8` | `INK_400` | 障碍 / 分隔 |
| `MD_INFO` | `#4F8FD6` | `INFO` | 被动 |
| `MD_WARN` | `#EB7866` | `ALLY_SOFT` | 警告 / 被掠夺 / 禁用 |

> ⚠️ **别在界面里写裸 hex 的 bbcode 色。** 这是踩过坑的：图鉴 / 故事正文原来硬编码了一批
> **纸面深色**（`#2e6b3c` `#7a5a10` `#55504a` `#403a2e` …），面板底转深色后立刻变成
> 「**深底深字，一个字都看不见**」—— 而这类问题**渲染之前完全无法察觉**。
>
> **J 段回归**会扫描全部界面脚本的 `color=#`，断言**每一处对卡片底对比度 ≥3.0**。
> 实测当前扫到 92 处、0 处不达标。改面板底色前先跑它。

## 六、改造记录（迁移是怎么做到零视觉变化的）

每个令牌的数值都**锚定在迁移前的硬编码值上**（注释里标了「← 原 xxx」）。所以：

| 类型 | 处数 | 视觉影响 |
|---|---|---|
| EXACT（值完全相同） | 155 | **逐像素不变** |
| MERGE（单通道差 ≤3%，肉眼不可辨） | 31 + 40 = 71 | 不可辨（ΔE &lt; 1，低于 JND） |
| 合计令牌化 | **226 处 / 21+ 个文件** | — |

归并掉的近似色（示例）：
`0.75,0.80,0.88` + `0.72,0.77,0.85` → `INK_250`；
`0.82,0.86,0.92` + `0.85,0.88,0.94` + `0.86,0.90,0.96` + `0.85,0.89,0.95` + `0.84,0.87,0.92` → `INK_200`；
`0.10,0.12,0.19,0.90` + `,0.97` → `SURFACE_PANEL`。

> ⚠️ **最重要的一条方法论**：**改「面板底色」绝不能只改底色**。
> 底色的**配套色**（正文色、bbcode 内联色、按钮皮肤、描边、遮罩）散落在几十处，
> 漏掉任何一类都会得到「看不见的字」。正确顺序是：
> **先枚举全部配套字面量 → 列成清单 → 逐条映射 → 每条带命中数断言 → 最后跑 J 段扫描**。
> 这次 61 处改动一次到位，靠的就是这个顺序。

> ⚠️ **我在第二轮引入并修掉过的一个回归**：批量替换时正则的**可选 alpha 分组**
> 把 `Color(0.965,0.948,0.905,0.78)` 的 **0.78 透明度吃掉了** → 图鉴列表页会变成不透明、
> 把背景视频整个盖住（那个半透就是为透出视频而设的）。
> **教训：批量替换颜色时，只要涉及"同一 RGB 但 alpha 不同"的用法，必须逐个核对。**
> （这类回归 test 抓不到，只能靠人眼 + 挨个比对原文。）

## 七、怎么扩展

1. **要新颜色** → 先在 `ui_design.gd` 加令牌。**不要在界面文件里写 `Color(...)`**（测试 E 段会抓住）。
2. **要新组件样式** → 加到 `ui_theme.gd` 的组件库区，不要在界面文件里手写 `add_theme_*_override`。
3. **改令牌值** → 等于全工程改色，属**显式设计决定**。改完必须跑 `tests/ui_design_smoke.gd`：A 段会红（提醒你这是有意的全量改色），届时同步更新 A 段的锚点值。
4. **字面量总数上限** 写在测试 E 段的 `_LITERAL_CEILING`（当前 170）。涨过它就说明在开倒车。
