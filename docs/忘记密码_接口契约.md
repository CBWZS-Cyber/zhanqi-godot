## 一、为什么要走这两条接口

现有线上能力（已核实、无需重做）：

| 已存在 | 说明 |
|---|---|
| `POST /send-code {email}` | 注册验证码。走 `127.0.0.1:8791` mail-gateway → QQ 邮箱 |
| `POST /bug-report` | Bug 上报直投 AgentMail |
| `REQUIRE_EMAIL_CODE` | 注册是否强制验证码（过渡档当前 `0`） |

**缺的只有「忘记密码」。** 它的地基已经在服务端了 —— 那条"**只绑定验证过的邮箱**"的设计
（过渡档里"填了邮箱但没走验证码"一律存空），正是为防止「谁都能填别人邮箱 →
忘记密码把重置信发到受害者信箱」。本契约依赖这条不变量。

## 二、第 ① 步：发重置码（复用现有路由）

```http
POST /send-code
Content-Type: application/json

{"name": "曹博文", "purpose": "reset"}
```

| 字段 | 说明 |
|---|---|
| `name` | **昵称**（不是邮箱）。服务端按 `uid = sha256(小写昵称)` 直接定位账号 |
| `purpose` | `"reset"` 区分用途；不传或 `"register"` 走原有注册分支（按 `email`） |

**成功 200**

```json
{"ok": true, "masked": "c***n@qq.com", "ttl": 300}
```

- `masked`：**该账号绑定的邮箱的掩码**，只用于界面提示"发到哪了"
- `masked == ""`：**该账号没有绑定邮箱** → 客户端会明确告知"无法自助找回，
  换台还记得密码的设备登录，或找作者重置"（**不是报错**，所以仍返回 `ok:true`）

**失败**：沿用现有错误形状 `{"ok": false, "error": "中文原因"}`，客户端直接显示。
建议覆盖：
- 昵称未填 / 账号不存在 → 统一文案（**不要**暴露"这个昵称存不存在"，避免昵称枚举）
- 触到重发冷却 / 发送上限 → 复用现有那些文案（"验证码刚发过，请 42 秒后再试"）

> ⚠️ 沿用现有的限流与冷却（同邮箱 5 封/天、同 IP 10 封/时 + 30 封/天、重发间隔 60 秒），
> **不要**为 reset 另开一套 —— 否则等于把发信额度翻倍给人刷。

## 三、第 ② 步：用码换新密码

```http
POST /reset-password
Content-Type: application/json

{"name": "曹博文", "code": "123456", "newpass": "newSecret123"}
```

**成功 200**

```json
{"ok": true, "token": "<新 token>", "account": {"uid": "...", "name": "...", "progress": {...}}}
```

- 客户端约定：**成功即视为已登录**（拿这个 `token` 直接进游戏，不再要求输一遍密码）
- 实现建议：重算 `salt` + `hashPass(newpass, salt)` 覆盖写；**不要**改 `uid` / `created` / `progress`
- 成功后**作废该账号所有未用的验证码**（reset 与 register 两类都清，防重放）

**失败 400 / 401**：`{"ok": false, "error": "..."}`，建议覆盖：
- 码不对 → 复用现有"验证码不对（还可试 N 次）"
- 码过期 → "验证码已过期，请重新获取"
- 新密码不足 6 位 → "密码需要 6~64 位"（与注册同一口径）
- 账号未绑邮箱 → "这个账号没有绑定邮箱，无法自助重置"

## 七、服务端实现记录（2026-10-05）

**改了什么**（全部是新增，**未改动任何既有分支**）：

| 位置 | 内容 |
|---|---|
| `handleSendCode` 首行 | 加 `purpose` 分流 —— **不传 `purpose` 时行为与改前逐字节一致**，老客户端注册码不受影响 |
| `handleSendResetCode()` | 新增：按昵称定位账号，**只发到账号自己绑定的邮箱** |
| `handleResetPassword()` | 新增：验码 → 重算 salt+hash → 保留 uid/name/created/email/progress → 下发 token |
| `maskEmailForUser()` | 新增：回给本人的掩码 `c***n@qq.com`（与日志用的 `maskEmail` 刻意分开，理由见函数注释） |
| `resetMailText()` | 新增：重置邮件正文（**与注册正文分开**，用户一眼能分辨是哪种码） |
| 路由表 / 文件头 | 注册 `/reset-password`；补上文件头漏写的 `/send-code`、`/bug-report` |

**两处刻意的顺序/回滚设计**（都是踩过的坑）：

1. `handleResetPassword` **先做本地校验（码格式、密码长度），再 `codeTake` 消费验证码**。
   反过来会让"密码太短"这种纯本地错误把码烧掉，用户白等 60 秒。已用断言锁住
   （同一个码在短密码被拒后仍然可用）。
2. 发信失败**回滚到发信前的完整状态**（含把旧码放回、退掉冷却与配额），与
   `handleSendCode` 里同一处修复同源。沙盒实测：邮件网关不可达 → 502 + 日志写明"旧码仍有效" + 进程不崩。

**验证**：本地测试台 65 断言 + 服务端沙盒 11 断言 + 生产真链路（见文首表格）。

**⚠️ 残留风险 1：可用于昵称枚举（有意接受）**
本接口对"存在且已绑邮箱"的昵称会回 `masked` ⇒ 拿得到掩码就等于确认昵称存在。
彻底消除只能一律回同一句"如果该账号存在，我们已发送重置邮件"，但用户就看不到"发到哪了"。
取舍依据：内测/朋友间的服务；且限流让枚举既慢又吵（**每次命中都会往对方信箱投一封真邮件**）。
公开运营时改成统一文案即可，**客户端无需改动**。

**⚠️ 残留风险 2：成功一次会清零该邮箱的冷却与日配额（既有问题，尚未修）**
`codeTake()` 把验证码记录**整条删掉**，而 `lastSent`（60 秒重发冷却）与 `dayN`（同邮箱 5 封/天）
就寄存在同一条记录上 ⇒ **每成功注册/改密一次，该邮箱的冷却与日配额都被清零**。
实测证据：注册码 `17:48:07` 发出，重置码 `17:48:36` 就发出去了（相隔 29 秒 ≪ 60 秒冷却）；
紧接着第三次请求被正常拦下（429「请 48 秒后再试」）⇒ 冷却本身有效，是"记录被删"造成的清零。
修法（**改动的是限流计数语义，属安全相关，需先批准**）：`codeTake` 不整条删除，
只清 `code`/`exp`/`tries`，保留 `lastSent`/`day`/`dayN`。注册与重置会一起受益。
